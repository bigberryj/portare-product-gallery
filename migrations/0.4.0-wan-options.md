# 0.4.0 — lazy Wan option storage (forward and rollback)

This version changes the plugin's use of existing WordPress options, **not** the SQL schema. There is no custom table, activation DDL, bulk metadata rewrite or SQL migration to run. `docs/schema.md` documents the option families and logical relationships.

## Forward

1. Back up the currently installed plugin and protected product/template records before staging deployment.
2. Install the candidate plugin and separately configure the fixed Node/Wan runtime; keep the access key in protected server configuration.
3. Leave existing `_ppg_setup`, gallery and Brizy values unchanged. The new non-autoloaded job/index/lock options are created only by authorized operations.
4. Retain the old aggregate `_ppg_ai_jobs` option. If the site previously submitted real MiniMax jobs, reconcile them first. Do not translate old task references into new paid Wan submissions.
5. Verify installed file hashes/version and product/template preservation. Read-only editor verification must not click product Update or Generate.

## Reverse

1. Stop new generation requests and account for every active or uncertain provider task before replacing code. A rollback does not cancel a paid provider task.
2. Restore the verified pre-deployment plugin archive, keeping all product metadata, attachments and job bookkeeping. Do not automatically delete `_ppg_ai_job_*`, `_ppg_ai_index_*` or lock records.
3. If the runtime must also roll back, restore the verified prior image/config as a separate operation. Remember startup-managed MU plugins on a persistent volume need explicit synchronized removal; an old image alone does not remove their copies.
4. Verify the restored plugin/version and public product rendering. Retained Wan attachments remain ordinary WordPress media and must not be deleted as rollback cleanup.

Manual pruning of job/lock records is a separate operator-authorized maintenance action after task reconciliation, never a way to force an uncertain paid request to retry.
